# 다음 시즌 준비

매달 새 책으로 시즌이 바뀐다. 이 절차는 2026년 9월 전환(프로세스 이코노미 → 꿈과 돈)에서
실제로 밟은 길을 그대로 굳힌 것이다. 그때 걸렸던 곳이 전부 여기 적혀 있다.

## 먼저 이해할 것 — 전환은 이미 자동이다

활성 시즌은 배포가 아니라 **시계**가 고른다. `startsAt`(KST)이 지난 시즌 중 가장 나중 것이
자동으로 켜진다. 그러니 이 작업의 목표는 "전환을 시키는 것"이 아니라
**전환 시각 전에 시즌을 config에 넣어 두는 것**이다. 넣어 두면 그날 새벽에 저절로 바뀐다.

## 일정 규칙 — 매달 같다, 묻지 않는다

- **매달 21일 시작, 28일(4주).** 시즌 JSON에 `"month": "2026-10"` 하나면 날짜가 전부 정해진다.
- **라이브는 각 주 7일째** = 7·14·21·28일차 22:00. 요일은 시작일 요일과 같다(9/21 월 시작 → 일요일 라이브).
- **회고 세션** = 종료 다음 날 ~ 다음 달 20일. 앱이 안내를 띄우고(인증은 닫힘), 정리본을 이때 보낸다.
- **커리큘럼**: 1일차 목차 훑기 → 2~19일차 1회독(라이브 날 빼고 16일) → 20일차 1회독 결산 →
  22~26일차 2회독 → 27일차 밑줄 총정리. 도구가 목차(`toc`)의 쪽수 비중으로 나눈다.
- 모집은 시작 3일 전 ~ 전날 23:59 (`recruitLabel`로 바꿀 수 있다).

## 받아야 하는 것

1. **책 정보** — 제목, 부제, 지은이·옮긴이·출판사, 표지 이미지, 판본(다른 판과 목차가 다른지)
2. **목차** — 캡처든 텍스트든. 장별 쪽수까지 있으면 분량이 더 고르게 나뉜다.
   (사용자가 직접 짠 노션 일정표가 있으면 그게 정본이다 — `readingPlan`으로 그대로 옮긴다)
3. **OT 영상 링크** (설명서 링크는 이 절차 안에서 노션에 만들어 받는다)
4. **신청자 명단** (.xlsx — 이름/이메일/전화번호)

없는 게 있으면 **추측하지 말고 물어본다.** 특히 저자명과 목차는 틀리면 멤버 전원이 본다.

## 절차

### 1. 목차를 옮긴다

캡처를 읽어 `toc`로 옮긴다: `[{ ch: '1장', title: '장 제목', s: ['소제목', …], pages: 60 }]`.
장 표기(`ch`)는 앱에 "1장 - 소제목"으로 보이니 짧게. 머리말·맺음말은 `ch: '머리말'`, `s: ['머리말']`.

지킬 것:
- **목차 글자를 바꾸지 않는다.** 소제목은 책에 적힌 그대로. 판본이 다르면 소제목이 다르다.
- 사용자가 노션 일정표를 직접 짰다면 **그게 정본이다.** `toc` 대신 `readingPlan`으로 그대로 옮긴다.
  이때 라이브 날은 "라이브 N회차"로 **시작**하게 쓰고, "발제문을 보고 [읽고 느낀 점]에 남기면 인증 완료"
  한 줄을 꼭 넣는다.
- 도구가 나눈 일자별 분량은 미리보기로 사람에게 보여 준다(한 날에 두 장이 걸치는 곳이 자연스러운지).

### 1.5. 발제문 초안을 쓴다

라이브 날마다 질문 3개 — `weeklyPrompts: [{ day: 7, questions: [...] }, …]`.
그 주 읽은 장의 핵심 개념을 **"내 브랜드·비즈니스에 적용하면"** 으로 바꾼 질문이어야 한다. 책 요약 질문은 안 된다.
3주차(21일차)는 완독 기념이라 "밑줄 BEST 10 중 하나만 남긴다면", 4주차(28일차)는 "28일 중 최고 문장과 실행".
말투는 `js/config.js` 시즌 1의 것을 잇는다(~해 보세요 / ~인가요?). 사용자가 라이브 전 주에 다듬는다.

### 2. 시즌 설명서(JSON)를 쓴다

`seasons/_예시.json`을 복사해 `seasons/<id>.json`으로 채운다. id는 `s3`, `s4`… 로 잇는다.
`month`만 적으면 날짜는 도구가 정한다. 앞 시즌 `lockAt`도 도구가 넣는다(전환 한 시간 뒤).

### 3. 시즌을 만든다

```
node tools/new-season.mjs seasons/<id>.json          # 미리보기
node tools/new-season.mjs seasons/<id>.json --write  # config.js + out/ 문서
```

`out/상세페이지.md` · `out/설명서.md` · `out/일정표.md` · `out/카톡공지.txt` 와 `out/노션게시.json`이 나온다.
**상세페이지는 전체 구조가 고정이고 책 제목과 "왜 이 책인가"만 바뀐다** — 그 부분만 손본다.
상세페이지 틀에는 9월 판에서 사람들이 빠져나가던 자리를 메운 단락이 다섯 군데 있다(`[보완]` 주석).
그 단락은 책과 상관없는 부분이니 지우지 않는다.

### 3.5. 노션에 올린다 — 사람이 붙여 넣지 않는다

`out/노션게시.json`에 파일·제목·아이콘·부모 페이지가 적혀 있다. 그 순서대로 `notion-create-pages`로 만든다.

- 부모는 「퍼메스 독서챌린지」 `3c2f15a6c51c80108cb1c88b5212be7d`. 다른 곳에 만들지 않는다.
- 올릴 때 HTML 주석(`<!-- -->`)은 뺀다. `(사진)` `(후기 캡처 …)` `(신청 링크 북마크)` 같은 자리표시 줄은
  **그대로 남긴다** — 사용자가 지난달 페이지에서 이미지·북마크를 끌어다 놓을 자리다.
- 설명서를 **먼저** 만든다. 만든 뒤 사용자가 노션에서 "웹에 게시"를 켜야 `notion.site` 링크가 생기고,
  그 링크가 시즌 JSON의 `guideUrl`(앱 상단 [설명서] 버튼)이 된다. 켜기 전까지는 링크가 열리지 않으니
  **사용자에게 게시를 켜 달라고 하고, 받은 링크로 config의 headLinks를 고친 뒤** PR을 연다.
- 만든 뒤 `notion-fetch`로 다시 읽어 표(일정표)·번호·굵게가 살아 있는지 본다. 번호 목록이 밀리면 고친다.
- 지난달 페이지는 건드리지 않는다. 새 페이지를 만든다.

### 4. 앞 시즌 잠금을 확인한다

도구가 앞 시즌의 `lockAt`을 새 시즌 전환 한 시간 뒤로 넣어 둔다. `git diff js/config.js`로 그 줄이
바뀌었는지만 본다. 그 시각이 지나면 앞 시즌은 참여자 화면에서 닫히고 운영진 화면에서만 열린다.

### 5. 검증한다 — 하나라도 빨간 채로 PR을 열지 않는다

```
npm run check:season   # 28일·라이브 요일·빈 회차·접두사 충돌·잠금 순서
npm test               # 로직
node test/ui.test.js   # 화면 (python3 -m http.server 8765 를 먼저 띄운다)
```

`test/ui.test.js`와 `test/logic.test.js`는 **시즌0에 고정**되어 있다(`pinSeason`).
새 시즌 때문에 이 고정이 깨지면 고정 쪽을 고치지, 시즌을 고치지 않는다.

### 6. 명단을 대조한다

```
node tools/roster-diff.mjs <신청자.xlsx> <카톡이름.txt>
```

**"번호 확인 후 결정"으로 나온 사람은 절대 자동으로 내보내지 않는다.** 한 글자 차이(고태윤 ↔ 고다윤)는
사람이 번호를 보고 갈라야 한다. 결제한 사람을 잘못 내보내는 것이 이 작업에서 가장 비싼 실수다.

명단은 도구로 넣는다 — 운영진 화면에서 파일을 고르지 않아도 된다.

```
node tools/roster-upload.mjs <신청자.xlsx> --season s3          # 미리보기
node tools/roster-upload.mjs <신청자.xlsx> --season s3 --write  # 넣기
```

`FIREBASE_SERVICE_ACCOUNT_KEY`(Netlify와 같은 서비스 계정 JSON)가 환경 변수에 있어야 한다. 없으면
운영진 화면 [명단 시트 업로드]로 사람이 넣는다 — **배너의 "보는 중: 시즌 N"이 새 시즌인지 먼저 확인.**
동명이인은 도구가 "이름(뒷4자리)"로 갈라 넣는다. 번호가 없어 못 가른 이름은 도구가 멈추고 알려 준다.

### 7. PR을 연다

무엇이 바뀌었는지, 무엇을 확인했는지, 사람이 봐야 할 게 무엇인지 적는다.
머지하면 Netlify가 자동 배포하고, 전환 시각에 저절로 시즌이 바뀐다.

## 매번 놓치는 것들

- **Firestore 보안 규칙** — 새 시즌은 `s3_participants` 같은 새 컬렉션을 쓴다. 규칙이 컬렉션
  이름을 하나씩 나열하는 방식이면 규칙을 넣기 전까지 **읽기·쓰기가 전부 막힌다.** README의
  이름 패턴을 쓰면 시즌이 늘어도 다시 안 고쳐도 된다.
- **표지 이미지** — 저장소에 파일을 넣어야 한다. `check:season`이 없으면 잡아 준다.
- **appUrl** — 실제 운영 주소와 같은지. 여기가 틀리면 리마인드 메일이 엉뚱한 곳으로 보낸다.
- **1일차** — 단톡방 입장 당일이라 `gradeFrom`으로 누락 집계에서 뺀다(도구가 자동으로 넣는다).
- **명단의 개인정보** — 신청자 xlsx/csv는 **저장소에 커밋하지 않는다.**

## 시즌이 끝날 때

- 운영진 화면 [알림 메일 › 🎁 선물 대상자]에서 누락 5회 이하 명단과 이메일을 복사할 수 있다(`giftMissLimit`).
- 라이브 대본 4개가 모이면 `live-insights` 스킬로 인사이트 정리본을 만들어 그 명단에 보낸다.

## 사람에게 넘길 것

작업이 끝나면 이것만 추려서 전한다.

1. PR 링크와 전환 시각
2. 노션에 만든 페이지 링크 셋 (설명서 · 일정표 · 상세페이지) — 설명서는 "웹에 게시"를 켜 달라고
3. 확인이 필요한 항목 (도구가 출력해 준다)
4. Firestore 규칙에 새 접두사가 열려 있는지
5. 명단 대조 결과 — 내보낼 사람 / 번호 확인이 필요한 사람 / 초대할 사람
